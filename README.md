# Stable Baselines3 SAC for a Dicke Quantum Battery

A Gymnasium + Stable-Baselines3 implementation of Soft Actor-Critic (SAC) for controlling the charging dynamics of a Dicke quantum battery. This project adapts the detuning-control setup discussed in:

> P. A. Erdman, G. M. Andolina, V. Giovannetti, and F. Noé,  
> “Reinforcement learning optimization of the charging of a Dicke quantum battery,”  
> arXiv:2212.12397 (2022; version 3, 2025).  
> https://arxiv.org/abs/2212.12397

The paper studies reinforcement learning for maximizing the single-TLS ergotropy of a Dicke battery by controlling either the light–matter coupling or the TLS–cavity detuning. This codebase implements the **detuning-control** variant. The original work provides a custom implementation of Soft Actor-Critic (SAC) for optimizing quantum battery charging. This project aims to make the implementation more accessible and easier to experiment with by adapting the original environment and training setup to the Stable-Baselines3 framework. It replaces the custom RL training infrastructure with SB3's standardized SAC implementation, while retaining the underlying Dicke battery dynamics, detuning-control formulation, and multi-objective reward structure as closely as possible.

## Model and control task

The environment represents a cavity mode coupled to an ensemble of \(N\) identical two-level systems (TLSs), restricted to the permutation-symmetric Dicke subspace. QuTiP is used to construct the operators and propagate the quantum state.

The controlled Hamiltonian has the detuning-control form

$$
\hat{H}(u(t)) = \hat{H}{_C} + \hat{H}{_\mathrm{int}} + (\omega_q + u(t))\hat{H}_{B},
$$

where $\hat{H}{_C}$ describes the cavity, $\hat{H}{_\mathrm{int}}$ represents the fixed light–matter interaction, and $\hat{H}_{B}$ is the bare TLS excitation operator. Here, $\omega_q$ is the nominal TLS transition frequency and $u(t)$ is the control signal generated by the RL agent.

The environment parameters include:

| Parameter | Meaning |
|---|---|
| `wc` | Cavity frequency |
| `wq` | TLS transition frequency |
| `nq` | Number of TLSs |
| `nc` | Cavity Fock-space truncation parameter |
| `nc_i` | Initial cavity photon number |
| `g` | Fixed light–matter coupling |
| `min_u`, `max_u` | Detuning-control bounds |
| `dt` | Duration of one control interval |
| `tau` | Target charging duration |
| `reward_coeff` | Scale applied to objective increments |
| `quantity` | Environment objective selector, where supported |

The initial state is a product of a cavity Fock state and the fully symmetric Dicke state with all TLSs in the ground state. The environment evolves the joint state with QuTiP and terminates an episode when the configured charging duration is reached.

### Observation

The observation is a flat `float32` vector containing:

1. Real components of the joint state vector.
2. Imaginary components of the joint state vector.
3. The previous control value.
4. The elapsed physical time.

For cavity cutoff `nc` and `nq` TLSs, the joint state-vector dimension is `(nc + 1) * (nq + 1)`. Therefore, the observation dimension is
$$
2(n_c+1)(N+1)+2.
$$
### Action

A one-dimensional continuous action representing the detuning control:

$$
u \in [u_{\min}, u_{\max}].
$$

The environment clips actions to the configured bounds before applying the Hamiltonian.

## Objectives and reward

The environment tracks two physical objective increments at every transition:

- Change in the total TLS energy.
- Change in the ergotropy of a single TLS, calculated from the single-TLS reduced density matrix.

They are exposed in the environment's `info` dictionary as:

```python
info["multi_obj"]          # [delta_energy, delta_ergotropy]
info["energy"]             # current total TLS energy
info["ergotropy"]          # current single-TLS ergotropy
info["control"]            # applied detuning
info["objective_weights"]  # current scalarization weights
```

SB3 SAC expects a scalar reward. The implementation therefore scalarizes the two objective increments at environment-step collection time:

$$
r_t = \mathbf{c}(t)\cdot
\begin{bmatrix}
\Delta E_t\\
\Delta \mathcal{E}_t
\end{bmatrix},
$$

where $\mathbf{c}(t)$ is interpolated between `C_START` and `C_END` using a logistic/Fermi schedule controlled by `C_MEAN` and `C_WIDTH`.

The schedule callback updates the environment's training-step counter and the SAC target entropy during training. The objective weights and target entropy are separate schedules.

## Installation

Python 3.10 or newer is recommended. Install the dependencies in the active virtual environment:

```bash
python -m pip install --upgrade pip
python -m pip install numpy scipy qutip gymnasium stable-baselines3[extra] torch pyyaml
```

The live training dashboard uses PyQtGraph and a Qt binding. Install these if the configured callback enables live plotting:

```bash
python -m pip install pyqtgraph PySide6
```

For CUDA training, install a PyTorch build compatible with the installed NVIDIA driver and CUDA runtime. Verify availability with:

```bash
python -c "import torch; print('CUDA available:', torch.cuda.is_available())"
```

## Configuration

Edit `training_config.yaml` to change the experiment. It is the source of truth for the physical parameters, SAC hyperparameters, schedules, logging, and checkpoint settings used by `train.py`.

Principal settings include:

| Setting | Purpose |
|---|---|
| Environment parameters | Cavity/TLS sizes, frequencies, coupling, control bounds, `dt`, and `tau` |
| `BATCH_SIZE` | Replay minibatch size |
| `LR` | SAC actor/critic learning rate |
| `ALPHA_LR` | Entropy-coefficient optimizer learning rate |
| `H_START`, `H_END`, `H_DECAY` | Target-entropy schedule |
| `C_START`, `C_END`, `C_MEAN`, `C_WIDTH` | Objective-weight schedule |
| `REPLAY_MEMORY_SIZE` | Replay-buffer capacity |
| `POLYAK` | Polyak averaging coefficient in the original parameterization |
| `GAMMA` | Discount factor |
| `HIDDEN_SIZES` | Actor and critic MLP hidden-layer sizes |
| `INITIAL_RANDOM_STEPS` | Initial random-action exploration steps |
| `TOTAL_TIMESTEPS` | Total environment interaction steps |
| `CHECKPOINT_FREQ` | Checkpoint callback frequency |
| Plot/logging options | Console report frequency, plot refresh frequency, and live/export settings |
| `USE_CUDA` | Whether to request CUDA when available |

When the configuration expresses the target-network coefficient as `POLYAK`, the SB3 constructor uses `tau = 1 - POLYAK`. The baseline uses `optimize_memory_usage=False`, since SB3 does not support combining `optimize_memory_usage=True` with timeout handling in the relevant replay-buffer configuration.

The exact values for a run are those in the checked-out `training_config.yaml`; this README does not duplicate them, so the YAML remains authoritative.

## Run training

From the repository root, with the virtual environment activated:

```bash
python train.py
```

`train.py` is the entry point. It loads the YAML configuration, constructs the Dicke battery Gymnasium environment, creates the SAC model and callbacks, and calls `model.learn(...)`. Depending on the options in the script/configuration, it may also validate the environment, wrap it with `Monitor`, and save the final model and replay buffer.

Run from the repository root so relative paths in the configuration and output directories resolve as intended.

## Outputs

Exact output paths are determined by `training_config.yaml` and `train.py`. The training setup is designed to produce:

- SAC model checkpoints.
- A final trained SAC model.
- A replay-buffer snapshot, if saving is enabled.
- Training plots and/or CSV metrics from the callback.
- TensorBoard event files, if a TensorBoard log directory is configured.

Inspect TensorBoard logs, if enabled, with:

```bash
tensorboard --logdir <tensorboard-log-directory>
```

## Resume and evaluation

A saved SB3 model can be loaded with the same environment definition and compatible observation/action spaces:

```python
from stable_baselines3 import SAC

model = SAC.load("path/to/model.zip", env=env, device="auto")
```

Use the same physical environment parameters as the training run. Evaluate deterministic actions separately from stochastic exploration, and report at least final TLS energy and single-TLS ergotropy. Retain the control trajectory and episode return when comparing charging protocols.

When continuing training from a checkpoint, load the corresponding replay buffer too if it was saved and replay continuity is required. Model weights alone do not restore replay-buffer contents.

## Reproducibility notes

- Record the complete `training_config.yaml` alongside each run.
- Record Python, PyTorch, Stable-Baselines3, Gymnasium, and QuTiP versions.
- Set and record random seeds for the environment and agent when comparing runs.
- Keep the cavity truncation sufficiently large and check that cavity population does not accumulate near the truncation boundary.
- Compare results at matched system size, charging time, and control constraints.
- Distinguish total TLS energy from single-TLS ergotropy: stored energy is not necessarily fully extractable as work.
- A successful training run does not by itself establish agreement with the paper's numerical results; the model, control protocol, reward schedule, and RL implementation details must also match.
